ข้อสังเกตหนึ่งเรื่อง

แคปชัน TikTok ที่ใช้อยู่ตอนนี้เป็นการยัด hashtag ติดกันเป็นพืด (#ยืดผมสมุทรปราการล#ยืดวอลุ่มบางปูล) — บนโซเชียลไม่เสียหาย แต่ ห้ามยกรูปแบบนี้มาลงบนเว็บ เด็ดขาด Google มองเป็น keyword stuffing เว็บใหม่จะใช้คีย์เวิร์ดชุดเดียวกันแต่เขียนเป็นประโยคที่คนอ่านรู้เรื่อง (§7.3)

อีกเรื่อง: เราหยิบ “ภาษาการออกแบบ” ของหน้าโปรดักต์ Apple มาใช้ — จังหวะการเล่าเรื่อง สเกลตัวอักษร ความสงบของเลย์เอาต์ — แต่ ไม่ใช้ฟอนต์ SF, ไม่ก็อปข้อความ, ไม่ใช้ภาพหรือไอคอนของ Apple ทุกภาพเป็นภาพถ่ายจริงของร้าน

§2

ทิศทางการออกแบบ: แปลหน้าโปรดักต์ ให้เป็นหน้าซาลอน

หน้า Mac mini ได้ผลเพราะมันไม่ใช่ “เว็บบริษัท” แต่เป็น เรื่องเล่าเรื่องเดียว ที่ปล่อยทีละบทตามการเลื่อนจอ แต่ละบทมีประโยคเดียว ภาพเดียว ความคิดเดียว เราจะเอากติกาเดียวกันมาใช้ โดยให้ “ยืดเคราติน” เป็นตัวเอกแทนตัวเครื่อง

§3

ดีไซน์ซิสเทมของเว็บ

3.1 สี

โครงสีมาจากโลกของงานผม: กระจกซาลอนให้แสงเย็น น้ำยาเคราตินให้ประกายทอง สีผมโทนม่วงอมแดงคือสีที่ร้านทำบ่อยที่สุด ดำสนิทใช้เป็นพื้นบท “โชว์ผลงาน” ขาวใช้เป็นพื้นบท “ให้ข้อมูล” สลับกันไปเหมือนหน้าโปรดักต์

Obsidian#0A0A0B พื้นบทมืด
Porcelain#FFFFFF พื้นบทสว่าง
Silk Plum#5E2A4F สีแบรนด์หลัก
Keratin Gold#C79A4B ตัวเลข/เน้น
Ash#6E6A73 ตัวอักษรรอง
LINE Green#06C755 ปุ่มจองเท่านั้น

เขียว LINE ใช้ที่ปุ่มจองอย่างเดียว ห้ามใช้ตกแต่งที่อื่น เพราะเราต้องการให้ “สีเขียว = กดแล้วได้คิว” ในหัวคนดู ส่วนม่วงพลัมใช้กับลิงก์ หัวข้อรอง และเส้นคั่น ทองใช้กับตัวเลขราคาและป้ายกำกับเท่านั้น

3.2 ตัวอักษร

ต้องรองรับไทยและอังกฤษด้วยบุคลิกเดียวกัน — ฟอนต์ไทยของ Google สองตัวนี้จับคู่กันได้พอดี

บทบาทฟอนต์ใช้ที่ไหน
หัวเรื่องAnuphan 600/700พาดหัวบท ตัวเลขใหญ่ ขนาด 40–96px ระยะอักษร -0.02em
เนื้อความIBM Plex Sans Thai 400/500คำบรรยาย รายละเอียดบริการ 17px/1.75 กว้างไม่เกิน 62 ตัวอักษร
ป้าย/ราคาIBM Plex Mono 500ป้ายหมวด เวลาเปิด ตารางราคา (tabular-nums)

สเกลตัวอักษร: 13 · 15 · 17 · 21 · 27 · 34 · 44 · 60 · 84 — ใช้เฉพาะค่าในสเกลนี้ ห้ามตั้งค่ากลาง ๆ เอง พาดหัวทุกอันใส่ text-wrap: balance

ทำที่ตอน implement

โหลดฟอนต์เองแบบ subset ภาษาไทยเป็น .woff2 ไว้ใน /assets/fonts/ อย่าดึงจาก Google Fonts CDN — ฟอนต์ไทยไฟล์ใหญ่ และการต่อโดเมนที่สามทำให้ LCP ช้าลง 200–400ms เอกสารฉบับนี้ดึงจาก CDN ได้เพราะเป็นแค่เอกสาร

3.3 เลย์เอาต์ กริด และมอชั่น

  • กริด 12 คอลัมน์ กว้างสุด 1280px ระยะขอบ 24px (มือถือ) / 40px (เดสก์ท็อป) บางบทปล่อยภาพเต็มจอ (full-bleed) เพื่อเบรกจังหวะ
  • เบรกพอยต์ 390 / 744 / 1068 / 1280 ออกแบบมือถือก่อนเสมอ — ลูกค้าร้านทำผมเข้าจากมือถือเกิน 90%
  • ความโค้ง 16px สำหรับการ์ดและภาพ · 999px สำหรับปุ่ม · บทเต็มจอไม่โค้ง
  • มอชั่น ใช้ IntersectionObserver ตัวเดียวจบ: เนื้อหาเลื่อนขึ้น 16px + จางเข้า 500ms เมื่อเข้าจอ 20% · ตัวเลขสเปกนับขึ้น · ตัวอักษรบทเปิดปรากฏทีละวลี · ทั้งหมดปิดอัตโนมัติเมื่อผู้ใช้ตั้ง prefers-reduced-motion
  • ห้าม พารัลแลกซ์แรง ๆ, สไลด์โชว์เลื่อนอัตโนมัติ, ป็อปอัปเด้งใส่, วิดีโอเปิดเสียงเอง — สี่อย่างนี้ทำให้เว็บดูถูกลงทันทีและกิน INP
§4

โครงสร้างเว็บและ URL

4.1 ข้อเสนอ: ภาษาไทยอยู่ที่ราก อังกฤษอยู่ที่ /en/

GitHub Pages ทำ 301 redirect ฝั่งเซิร์ฟเวอร์ไม่ได้ ถ้าวางไทยไว้ที่ /th/ ตามสูตรมาตรฐาน หน้าแรก / จะต้องเด้งด้วย JavaScript หรือ meta refresh ซึ่งเป็นจุดอ่อนที่สุดของเว็บทั้งเว็บ — หน้าที่ได้ลิงก์เข้ามากที่สุดกลับเป็นหน้าที่ไม่มีเนื้อหา ทางออกที่สะอาดกว่าคือให้ ไทยเป็นภาษาที่รากเลย ตลาดจริงของร้านคือคนสมุทรปราการอยู่แล้ว

กติกา URL

  • ตัวพิมพ์เล็ก ขีดกลาง ปิดท้ายด้วย / เสมอ (GitHub Pages เสิร์ฟ index.html ในโฟลเดอร์ให้อยู่แล้ว) เลือกแบบใดแบบหนึ่งแล้วห้ามสลับ
  • slug เป็นภาษาอังกฤษ ถึงหน้าจะเป็นภาษาไทย — slug ไทยติดอันดับได้จริง แต่พอแชร์ใน LINE/Facebook จะกลายเป็น %E0%B8%A2… ยาวเหยียดและอ่านไม่ออก ส่วนคีย์เวิร์ดไทยไปอยู่ใน <title>, H1 และเนื้อหาซึ่งมีน้ำหนักกว่ามาก
  • หนึ่งบริการ = หนึ่งหน้า ห้ามยัดทุกบริการไว้หน้าเดียว — 6 หน้าบริการคือ 6 ประตูทางเข้าจาก Google
  • ร้านมีที่เดียว จึงมีหน้าที่ตั้งหน้าเดียว ห้ามสร้างหน้าแยกรายพื้นที่ (บางปู ตำหรุ สำโรง) ทั้งที่ไม่มีร้านอยู่ตรงนั้น Google เรียกหน้าแบบนั้นว่า doorway page และลงโทษ — พื้นที่พวกนี้ใส่เป็น areaServed กับพูดถึงในเนื้อหาแทน
  • ไม่มีพารามิเตอร์ต่อท้ายที่ทำให้เกิดหน้าซ้ำ ยกเว้น UTM ที่ต้องมี canonical กันไว้

§6

หน้าอื่น ๆ

6.1 หน้าบริการ (แม่แบบเดียว ใช้ซ้ำ 6 หน้า)

นี่คือหน้าที่จะดึงทราฟฟิกจาก Google มากที่สุด ไม่ใช่หน้าแรก โครงคงที่ทุกหน้าเพื่อให้ทั้งคนและบอทคาดเดาได้:

  1. Breadcrumb: หน้าแรก › บริการ › ยืดเคราติน
  2. Hero ย่อ: H1 + ราคา + ระยะเวลา + ปุ่มจอง (เห็นราคาโดยไม่ต้องเลื่อน)
  3. “เหมาะกับผมแบบไหน” — เช็กลิสต์ 4–5 ข้อ ให้คนอ่านทักตัวเองได้
  4. ผลงานจริง 4–6 ภาพ ก่อน–หลัง พร้อม alt ภาษาไทยที่บรรยายจริง
  5. ขั้นตอน + เวลาที่ใช้ในร้าน
  6. ราคาแยกตามเงื่อนไข + สิ่งที่รวมอยู่แล้ว (ตัดแต่ง/บำรุง)
  7. วิธีดูแลผมหลังทำ 5 ข้อ — ส่วนนี้ดึงคีย์เวิร์ดหางยาวได้เยอะ
  8. คำถามที่พบบ่อยของบริการนี้ 5–8 ข้อ (<details> ที่ยังอ่านได้ตอนปิด)
  9. ลิงก์ไปบริการใกล้เคียง 3 อัน + ปิดท้ายด้วยปุ่มจอง

6.2 หน้าที่ตั้งร้าน (หน้าที่สำคัญที่สุดสำหรับ Local SEO)

ร้านมีที่เดียว จึงมีหน้านี้หน้าเดียว และต้องอัดให้แน่น: ที่อยู่เต็ม · พิกัด · เวลาเปิด · เบอร์โทร · ภาพหน้าร้าน ภายในร้าน และทีมช่าง · วิธีเดินทางเขียนเป็นภาษาคน (“ออกทางออก 2 เดินตรงมา 200 เมตร อยู่ติดร้าน…”) · จุดสังเกตแถวนั้น · ที่จอดรถ · JSON-LD HairSalon เต็มตัวหนึ่ง

ลูกค้าจำนวนมากเดินทางมาจากบางปู ตำหรุ และสำโรง ให้พูดถึงพื้นที่พวกนี้ในหน้านี้อย่างตรงไปตรงมา (“ลูกค้าจากบางปูนั่ง BTS มาลงเคหะฯ ประมาณ 15 นาที”) — ได้สัญญาณท้องถิ่นโดยไม่ต้องสร้างหน้าปลอมรายพื้นที่

6.3 หน้าราคา

ตารางราคาเดียวทั้งเว็บ อัปเดตที่เดียว หน้าอื่นลิงก์มา · แยกหมวด ยืด/ดัด/ทำสี/บำรุง · แต่ละแถวลิงก์ไปหน้าบริการ · ระบุวันที่อัปเดตราคาล่าสุด (สร้างความน่าเชื่อถือ และ Google ชอบสัญญาณความสด) · ถ้าราคาต่างกันตามสาขา ต้องแยกคอลัมน์ให้ชัด

6.4 บล็อก — ไม่ใช่ของแถม แต่คือเครื่องมือหาลูกค้าใหม่

คนยังไม่พร้อมจองจะค้นคำถามก่อน ห้าบทความแรกที่ควรเขียน (แต่ละบทความจบด้วยลิงก์ไปหน้าบริการที่เกี่ยวข้อง):

  1. ยืดเคราติน กับ ยืดวอลลุ่ม ต่างกันยังไง เลือกแบบไหนดี
  2. ผมฟอกจนขาด ยังยืดได้ไหม — เชื่อมแกนผมช่วยยังไง
  3. ยืดผมใช้เวลากี่ชั่วโมง ต้องเตรียมตัวยังไงบ้าง
  4. ดูแลผมยังไงให้ยืดอยู่นาน 6 เดือน
  5. รวมราคาทำผมย่านสมุทรปราการ ปี 2569 ควรจ่ายเท่าไรถึงเรียกว่าคุ้ม
§7

SEO เต็มรูปแบบ

แบ่งเป็น 7 ชั้น ทุกชั้นต้องทำ ไม่ใช่เลือกทำ — ชั้นที่คนชอบข้ามคือ 7.5 (Local) ซึ่งดันเป็นชั้นที่ให้ลูกค้าจริงมากที่สุดสำหรับธุรกิจแบบนี้

7.1 ชั้นเทคนิค

รายการวิธีทำ
Canonicalทุกหน้าใส่ <link rel="canonical"> เป็น URL เต็มแบบสัมบูรณ์ ชี้ตัวเอง (กัน UTM ทำให้เกิดหน้าซ้ำ)
hreflangทุกหน้าประกาศครบ 3 บรรทัด: th, en, x-default → ชี้ไทย · ต้องชี้กลับหากันทั้งสองฝั่ง ไม่งั้น Google ไม่นับ
Sitemap/sitemap.xml รวมทุกหน้าทั้งสองภาษา + <lastmod> จริง · เพิ่ม image extension ให้หน้าผลงาน
robots.txtเปิดหมด + ระบุ sitemap · ห้ามเผลอ Disallow: / ตอน deploy
404/404.html — GitHub Pages ส่งสถานะ 404 จริงให้ ไม่ใช่ soft 404 · ใส่ลิงก์บริการยอดนิยม
HTTPSเปิด “Enforce HTTPS” ใน GitHub Pages · เลือก www หรือไม่มี www อย่างใดอย่างหนึ่งแล้วยึดตลอด
เนื้อหาไม่พึ่ง JSทุกข้อความและทุกลิงก์อยู่ใน HTML ตั้งแต่แรก JS ทำแค่มอชั่นกับการโต้ตอบ · ปิด JS แล้วต้องอ่านได้ครบและจองได้
Mobileviewport ถูกต้อง · เป้ากดขนาด ≥44px · ไม่มี horizontal scroll · ตัวอักษรพื้นฐาน ≥16px
เมตาที่ต้องมีทุกหน้าtitle, description, og:*, twitter:card, lang, theme-color, favicon ครบชุด

7.5 ชั้น Local SEO — ชั้นที่ให้ลูกค้าจริงมากที่สุด

สำหรับร้านทำผม อันดับใน Google Maps สำคัญกว่าอันดับในผลค้นหาปกติ เว็บมีหน้าที่สองอย่าง: เป็นหลักฐานยืนยันข้อมูลร้าน และเป็นปลายทางของลิงก์จาก Maps

  • Google Business Profile — ยืนยันตัวตนแล้ว หมวดหลัก “ร้านทำผม/Hair salon” หมวดรอง “Beauty salon” · ลิงก์เว็บชี้หน้าแรกพร้อม UTM · ถ้าเคยสร้างโปรไฟล์ของสาขาบางปูไว้ ต้องตั้งเป็น “ปิดถาวร” ไม่ใช่ปล่อยทิ้ง โปรไฟล์ค้างที่ไม่มีร้านจริงทำให้ลูกค้าไปเก้อแล้วได้รีวิวหนึ่งดาว
  • NAP ตรงกันเป๊ะทุกที่ — เว็บ / GBP / Facebook / TikTok bio ต้องสะกดชื่อร้าน ที่อยู่ และเบอร์เหมือนกันตัวต่อตัว รวมถึงรูปแบบเบอร์
  • รีวิว — ตั้งเป้าขอรีวิวจากลูกค้าที่พอใจสัปดาห์ละ 3–5 ราย ด้วย QR ที่โต๊ะแคชเชียร์ · ตอบทุกรีวิวภายใน 48 ชั่วโมง · ห้ามซื้อรีวิว
  • รูปใน GBP — ลงงานจริงสัปดาห์ละ 2–3 รูป โปรไฟล์ที่ลงรูปสม่ำเสมอได้เปรียบชัดเจน
  • Local citation — Wongnai, Google Maps, Apple Maps, Facebook Page, TikTok bio, สมุดหน้าเหลืองออนไลน์ · ทุกที่ลิงก์กลับมาที่โดเมนใหม่
  • เนื้อหาอิงพื้นที่ — พูดถึงสถานที่จริงแถวนั้น (สถานี ทางออก นิคมฯ ห้างใกล้เคียง) ในหน้าที่ตั้งร้าน นี่คือสัญญาณท้องถิ่นที่คู่แข่งส่วนใหญ่ไม่ทำ

7.6 ชั้นภาพและวิดีโอ

ร้านทำผมขายด้วยภาพ และภาพคือทั้งจุดแข็งด้าน SEO และตัวการทำเว็บช้าที่สุด กติกา:

  • ทุกภาพส่งออก 3 ขนาด (480 / 960 / 1600) เป็น AVIF + WebP + JPG สำรอง ผ่าน <picture> + srcset
  • ระบุ width/height ทุกครั้ง — กัน CLS · ทุกภาพที่ไม่ใช่ hero ใส่ loading="lazy" decoding="async"
  • ชื่อไฟล์บอกเรื่อง: keratin-straightening-before-after-01.avif ไม่ใช่ IMG_2934.jpg
  • alt ภาษาไทยที่บรรยายภาพจริง เช่น “ผมยาวประบ่าหลังยืดเคราติน เงาตรงไม่ลีบ” — ไม่ใช่ที่ยัดคีย์เวิร์ด
  • คลิป before/after: โฮสต์เอง .mp4 H.264 ปิดเสียง playsinline เล่นเมื่อเข้าจอ ยาวไม่เกิน 8 วินาที ไฟล์ไม่เกิน 1.5MB · อย่าฝัง iframe TikTok บนหน้าแรก มันลาก JS มาหลายร้อย KB

7.7 ชั้นวัดผล

เครื่องมือตั้งค่าอะไร
Google Search Consoleยืนยันโดเมน · ส่ง sitemap · ดูรายงาน Core Web Vitals · เช็กคีย์เวิร์ดจริงเดือนละครั้ง
GA4อีเวนต์: click_line, click_phone, click_map, view_pricing, play_before_after, drag_compare · ตั้ง click_line กับ click_phone เป็น key event
Bing Webmasterยืนยัน + ส่ง sitemap (ใช้เวลา 5 นาที ได้ทราฟฟิกฟรีเพิ่ม)
UTMลิงก์จาก GBP / TikTok bio / Facebook ใส่ UTM ทุกอัน จะได้รู้ว่าลูกค้ามาจากไหนจริง ๆ

ตัวชี้วัดที่ควรดู ไม่ใช่จำนวนคนเข้าเว็บ แต่คือ จำนวนคลิกปุ่ม LINE ต่อสัปดาห์ และ อันดับใน Maps สำหรับคำว่า “ร้านทำผมใกล้ฉัน” ในรัศมี 3 กม. — สองตัวนี้แปลเป็นคิวจริงได้ตรงที่สุด

งบประมาณความเร็ว และการเข้าถึง

8.1 เพดานที่ห้ามเกิน

ตัวชี้วัดเป้าวิธีคุม
LCP< 2.0s (4G)preload ภาพ hero, fetchpriority="high", AVIF, ฟอนต์โฮสต์เอง, ไม่มี JS บล็อกการเรนเดอร์
CLS< 0.05ระบุขนาดภาพ/วิดีโอทุกอัน · font-display:swap + size-adjust · จองที่ให้แผนที่ก่อนโหลด
INP< 200msJS ทั้งเว็บไม่เกิน 30KB gzip · listener แบบ passive · ไม่มีเฟรมเวิร์ก
CSS< 25KB gzipไฟล์เดียว ไม่มี framework · critical CSS ฝังใน <head>
น้ำหนักหน้าแรก< 900KB ตอนโหลดครั้งแรกคลิปและภาพล่าง ๆ โหลดแบบ lazy ทั้งหมด
Lighthouse≥ 95 ทั้ง 4 หมวด (มือถือ)รันเป็น GitHub Action ทุกครั้งที่ push · ถ้าตกให้ build แดง

8.2 การเข้าถึง (มีผลกับ SEO ด้วย)

  • คอนทราสต์ผ่าน WCAG AA ทั้งบทมืดและบทสว่าง — โดยเฉพาะตัวอักษรทับภาพ ต้องมีชั้นไล่สีรอง
  • ใช้แท็บคีย์บอร์ดได้ครบ รวมถึงสไลเดอร์ก่อน–หลังและการ์ดเลื่อนแนวนอน · โฟกัสต้องมองเห็น
  • แลนด์มาร์กครบ (header/nav/main/footer) + ลิงก์ “ข้ามไปเนื้อหา”
  • ทุกอย่างที่กดได้เป็น <a> หรือ <button> จริง ไม่ใช่ <div onclick>
  • เคารพ prefers-reduced-motion — ปิดมอชั่นทั้งหมด เนื้อหายังครบ
  • ฝั่งอังกฤษต้องแปลจริงโดยคน ไม่ใช่แปลเครื่องแล้วปล่อย · หน้า EN ที่แปลลวก ๆ แย่กว่าไม่มีหน้า EN

ข้อแลกเปลี่ยนที่ต้องตัดสินใจ

Static HTML ล้วนแปลว่า header/nav/footer จะถูกคัดลอกซ้ำใน ราว 30 ไฟล์ (15 หน้า × 2 ภาษา) วันที่เปลี่ยนเบอร์โทรหรือเพิ่มเมนู ต้องแก้ 34 จุด และพลาดจุดเดียว NAP ก็ไม่ตรงกันทันที ซึ่งกระทบ SEO โดยตรง

ทางออกที่ผมแนะนำ: เขียนสคริปต์ Node สั้น ๆ (~60 บรรทัด ไม่มี dependency) ที่แทนที่ <!--#include head--> ด้วยไฟล์ partial แล้วให้ GitHub Actions รันตอน push · ผลลัพธ์ที่ deploy ยังเป็น HTML ล้วนเหมือนเดิมทุกประการ ความเร็วไม่เปลี่ยน แต่แก้ที่เดียวจบ · ถ้าอยากเลี่ยง build จริง ๆ ทางเลือกสำรองคือให้ JS ประกอบ footer ตอนรันไทม์ — ไม่แนะนำ เพราะ NAP จะไม่อยู่ใน HTML ซึ่งเสียประโยชน์ Local SEO ที่เป็นหัวใจของงานนี้

ขั้นตอน deploy

  1. ตั้ง GitHub Pages ชี้ที่ branch main (หรือ Actions ถ้าใช้สคริปต์ประกอบไฟล์)
  2. เพิ่มไฟล์ CNAME · ตั้ง DNS ที่ผู้ให้บริการโดเมน: A 4 เรคคอร์ดของ GitHub Pages + CNAME สำหรับ www
  3. รอใบรับรอง แล้วเปิด Enforce HTTPS
  4. ยืนยันโดเมนใน Search Console + ส่ง sitemap
  5. อัปเดตลิงก์ใน Google Business Profile, TikTok bio และ Facebook
